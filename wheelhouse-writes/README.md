# Wheelhouse Writes

Write-capable guidance for the Wheelhouse Revenue Management API/MCP: the procedural knowledge needed to make changes safely, not just read data. Companion to the read-only `wheelhouse-plugin` (sync/cache/leaderboard skills) — kept as a separate plugin deliberately, so a client's decision to let Claude *read* their Wheelhouse data and their decision to let Claude *write* to it stay two distinct choices.

## What's in this plugin

Three write surfaces, each with an interactive (MCP) skill and an unattended (direct-API) sibling; one migration/translation skill for a narrower audience; and two shared references:

| Skill | Covers |
|---|---|
| `context-preferences` | Pricing-engine settings via the connected Wheelhouse MCP: base price, seasonality, day-of-week, min/max price, min stay, demand sensitivity, historical anchoring, check-in/check-out, long-term discounts, occupancy pacing. Rule hierarchy, fetch-then-merge, per-channel setting support. Interactive — confirms before every write. |
| `context-preferences-api` | Same settings surface, for scripts calling the RM API directly with an API key outside a chat turn. Dry-run by default; writes only with an explicit `--apply` flag after the client reviews a printed diff. |
| `context-events-seasons` | Season/Event date-range definitions (`custom_date_ranges`) and the seasonal/event rules that reference them, via the MCP. The id-sharing model and the blank-id protocol for definition changes vs. value-only changes. Interactive, confirms before every write. |
| `context-events-seasons-api` | Same, scripted. Dry-run by default, prints the full id-migration plan before any `--apply`. |
| `context-custom-rates` | Custom Rate date-range overrides via the MCP: fixed vs. adjustment types, overlap/split behavior, the exact compounding math for combining a new instruction with an existing rate. Interactive, confirms the specific values before every write. |
| `context-custom-rates-api` | Same, scripted. Dry-run by default, shows the computed combine math and exactly which existing rate periods would be shortened/split before any `--apply`. |
| `context-pricelabs-migration` | Translation-only skill (no writes of its own) for a client whose vocabulary or expectations come from PriceLabs or another pricing tool: "Customization" → Wheelhouse preference rule, "Pricing Profile" → Season/Event entry + bundle of rules, "Date-Specific Override" → Custom Rate. Flags the single behavioral difference most likely to surprise a migrating client — PriceLabs Customizations stack by default, Wheelhouse preference rules resolve by strict precedence and Custom Rates replace/split — then hands off to the owning skill above for the actual write. |

`references/lexicon-disambiguation.md` is loaded by all six write-capable skills. It resolves the terminology gap between how a Wheelhouse-native client talks about their pricing ("seasonal rate," "custom rate," "channel," "base rate," "replace vs. combine") and what those words map to in the API/database — written for an audience that knows revenue management but not Wheelhouse's specific object model. It's deliberately scoped to Wheelhouse-native and general-industry language; platform-specific vocabulary (PriceLabs, etc.) lives in `context-pricelabs-migration` instead, per its own `references/pricelabs-customization-map.md`.

## Design decisions worth knowing if you extend this

- **Split by write surface, not by endpoint.** Preferences (~10 UI-visible settings) share one procedural model (rule hierarchy, fetch-then-merge) and are one skill; Custom Rates and Events & Seasons each have genuinely different semantics (no rule hierarchy; an id-lifecycle problem) and are separate skills. Don't add another skill per additional preference setting — extend `context-preferences` instead, unless the new setting has a genuinely different write model.
- **The PriceLabs migration skill is translation-only, not a fourth write surface.** It doesn't get an `-api` sibling, because it never writes anything itself — it identifies which of the other three write surfaces a PriceLabs-flavored request actually targets, then hands off. If a future addition needs the same treatment for a different platform (Key Data, a client's own legacy tool), follow this same pattern: one translation skill, no write mechanics duplicated, references the write-capable skills rather than restating their protocols.
- **MCP and direct-API variants are deliberately separate skills, not one skill with a mode flag.** Their safety models are different in kind, not just mechanism: the MCP skills lean on live conversational confirmation; the API skills lean on dry-run/`--apply` because there's no one to confirm with in an unattended run. Collapsing them would blur that distinction exactly where it matters most.
- **The lexicon reference is plugin-root-level, not duplicated per skill**, so all six write-capable skills stay in sync on terminology as Wheelhouse's product language evolves. If you edit it, you're editing it for all six at once — check that a change doesn't contradict a skill-specific nuance before publishing. It's deliberately scoped to Wheelhouse-native/general-industry terms only — resist the temptation to fold platform-specific vocabulary back into it; that belongs in `context-pricelabs-migration` (or an analogous future skill) instead, so this file doesn't dilute for the audience that never needs it.
- **Every write-capable skill defaults to confirm-before-write (MCP) or dry-run (API), with no built-in unattended bypass beyond what the client explicitly configures.** If a future addition to this plugin loosens that default, treat it as a deliberate, flagged decision, not a convenience shortcut.
- **Rate-limit guidance is centralized in `context-preferences-api/SKILL.md`, not duplicated per `-api` skill** (`context-custom-rates-api`/`context-events-seasons-api` just cross-reference it) — and it's written to stay correct across a future limit change rather than stating the current ceiling as a fact. The limit has already changed once (20/min → 60/min) and a token-level dimension is under consideration; the guidance tells a script to read `X-RateLimit-*` headers live and never bake in today's specific number. If you extend any script guidance in this plugin, keep that same discipline — a hardcoded number here is the kind of thing that goes stale silently.

## Verification status

Tool names, parameter shapes, rule-array schemas, and the direct-API base URL/endpoints/rate-limit facts in this plugin were checked live against the connected Wheelhouse MCP (`Wheelhouse:search`/`get_schema`) and the RM API docs (`api.usewheelhouse.com/wheelhouse_rm_api`) as of 2026-09-15.

**Live-tested 2026-09-15** (real listing, `wheelhouse_id: 64765806`, channel `hypothetical`), beyond schema-only verification:
- `wheelhouse_rmBulkPutCustomRates` — bulk-wrote two non-overlapping custom rates (one `fixed`, one `adjustment`) in a single call; both landed correctly on read, no unintended splits against the listing's three pre-existing rates. Confirmed the actual response shape (previously opaque in the schema): `{"updated_custom_rates": [...]}`.
- `wheelhouse_rmBulkDeleteCustomRates` — cleanly removed both test rates in one call; listing reverted to exactly its pre-test state on read. Confirmed the response is an empty body, not a JSON object.
- The overlap/split/replace behavior documented in `context-custom-rates/SKILL.md` is independently corroborated by this listing's real `wheelhouse_rmGetPreferencesChangelog` history, which records past events like "Fixed rate split off," "Automated rate split off" matching the documented mechanics exactly.
- `wheelhouse_rmPutPreferences` with a new `custom_date_ranges` entry (`id` omitted) — confirmed the server assigns a new id (a UUID) and, critically, **returns it directly in that same PUT's response body** (the full updated preferences object), so `context-events-seasons`/`-api`'s create-then-reference workflow needs no separate `GetPreferences` call to learn the assigned id. Cleaned up afterward (a second PUT with `custom_date_ranges: []`) and confirmed via read that the listing reverted to its pre-test state.

Two residual gaps remain, narrower than before:

1. **The literal direct-API HTTP path** for bulk Custom Rates (`PUT /listings/{listing_id}/custom_rates/bulk`) is still unconfirmed by a live call — the MCP abstracts transport, so testing `wheelhouse_rmBulkPutCustomRates` (above) confirms the *operation's behavior* but not the *exact REST path* the `context-custom-rates-api` skill documents for direct-API clients. That still needs either a raw HTTP call with an API key or a fresh docs pull to fully close.
2. The RM API's own public `#tag/Changelog` page (dated release notes for the API itself) wasn't fully retrievable during this build. Distinct from the per-listing changelog above (which *is* now live-confirmed) — this is about whether anything shipped in the API very recently that isn't yet reflected in this plugin's documentation. Still worth a re-check before wide distribution.

This is a beta API; re-verify tool schemas periodically rather than treating this plugin as permanently current.

**`context-pricelabs-migration` was verified against PriceLabs' help-center documentation (fetched 2026-09-15), not against a PriceLabs account or API.** Its Wheelhouse-side field mappings reuse the same live-checked facts as the rest of this plugin, but a handful of entries in `references/pricelabs-customization-map.md` are explicitly marked ⚠️ needs verification — PriceLabs customizations (Rounding, Smoothing, Weekend Days, Pricing Offset-as-final-step) with no confirmed Wheelhouse equivalent found during this build. Don't tell a client one of these definitely doesn't exist in Wheelhouse without checking the current schema first.
