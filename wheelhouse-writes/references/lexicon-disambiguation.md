# Wheelhouse Write-Operations Lexicon & Disambiguation

Shared reference for every skill in this plugin. Load this before interpreting any user request that names a setting, rate, or date range to change. Its job is narrow: catch the cases where a client's everyday phrase does **not** map onto the Wheelhouse object you'd guess from the words alone. Where a phrase is unambiguous, don't call this out to the user — just use the right term silently and move on. Where it's ambiguous, resolve it explicitly before writing anything, per each skill's own confirmation step.

The test for whether something belongs on this page: would a client fluent in general STR/revenue-management language, but with no idea how Wheelhouse's API or database is put together, reasonably mean something different from what the API field name suggests? If yes, it's an entry here. Terminology that's simply "the canonical name for a metric" (ADR, RevPAR, etc.) lives in the project's own Lexicon (§3 of project instructions) — this file is specifically about **write-target** ambiguity, not metric-reading ambiguity.

## How to use this file

1. Before calling any write tool, check whether the user's request contains a phrase in the left column below.
2. If it does, do not silently pick one meaning. State your interpretation back to the user as part of the confirmation step every write already requires ("by 'seasonal rate' I'm reading this as Wheelhouse's Seasonal rule type on the Winter Holidays date range — is that right, or did you mean the general winter pricing level?"), unless the rest of the user's sentence already disambiguates it unambiguously (e.g. they say "add a rule under Events & Seasons" — that's already the Wheelhouse-specific sense, no need to re-ask).
3. When in doubt between two readings, prefer asking over guessing. A wrong write here is a live pricing change on a client's account, not a cosmetic mistake.

## Ambiguous terms

### "Preferences" / "Settings"
- Wheelhouse's own RM API docs state this directly: the object every skill in this plugin calls **`preferences`** is labeled **"Settings"** in the Wheelhouse app itself. "Preferences" is API/internal vocabulary — a client will almost never say it. Expect "change my settings," "update my pricing settings," or a specific UI group name (Pricing Engine, Limits, Operations, Calendar Pacing, Configuration — see Context-Preferences' settings table) rather than the word "preferences." Not a source of write-target ambiguity in the sense of picking the wrong object, but worth knowing so a confirmation message doesn't lead with unfamiliar API jargon ("I'll update your preferences" reads oddly to a client who has only ever seen "Settings" in the app) — mirror the client's own word back when confirming.

### "Seasonal rate" / "seasonal pricing" / "season rate"
- **Could mean:** (a) a rule using Wheelhouse's `seasonal` rule `type`, tied to a Seasons & Events entry (Context-Events&Seasons); or (b) nothing Wheelhouse-specific at all — just "the rate during a particular demand season" (e.g. "our summer rate"), which in Wheelhouse terms could be a `seasonal` rule, a `monthly` rule, a `custom` date-range rule, or even a Custom Rate, depending on how the client already has it modeled.
- **Resolve by:** asking whether they mean the Events & Seasons feature specifically, or just "prices during [named period]" generically. If generic, find out whether a matching Season/Event already exists (`custom_date_ranges`) before deciding which rule type to use — see the placement decision logic in Context-Events&Seasons.
- A client whose vocabulary comes from another pricing tool (e.g. "seasonal profile," "pricing profile") rather than general RM language — see **Context-PriceLabsMigration** for that translation instead of guessing here.

### "Custom rate" / "custom pricing" / "custom price"
- **Could mean:** (a) a Wheelhouse Custom Rate object (`PutCustomRate`/`BulkPutCustomRates`) — a date-range override that replaces/splits, doesn't participate in the rule hierarchy; or (b) colloquial shorthand for "I want to set a specific price" that actually belongs as a `custom`-type rule inside `minimum_price_rules_v3`/`maximum_price_rules_v3`/`day_of_week`/etc. — a rule, not a Custom Rate object.
- **Resolve by:** the giveaway is whether the client wants a one-off override for specific dates that should win regardless of the pricing engine's other rules (→ Custom Rate object, Context-CustomRates) vs. wants to change what the *engine itself* recommends going forward (→ a preference rule, Context-Preferences). "Set my rate to $400 for July 4th weekend no matter what" is a Custom Rate. "Always charge more on July 4th weekend every year" is a `custom` or `event` rule in preferences. A one-off date-specific *rule* rather than a recurring one is still a preference rule, not a Custom Rate — the app's own front end calls that a "Date Specific" rule; see the "Replace/override/update" entry below for that distinction spelled out in full, since clients often use "override" for either object interchangeably.

### "Customization" / "Customizations"
- If a client uses "customization" as a generic word for "a rule I've set up," treat it the same as "rule" or "setting" — see Context-Preferences. If it's clearly a term of art from another platform they're migrating from (most often PriceLabs, where "Customizations" is a specific umbrella feature name with its own stacking behavior, genuinely different from how any Wheelhouse write object works), don't guess the mapping here — see **Context-PriceLabsMigration**, which exists specifically to translate that vocabulary and flag the stacking-vs-precedence difference before anything gets written.

### "Minimum stay" / "min stay" / "minimum length of stay" / "MLOS"
- **"MLOS" is the client's own shorthand for minimum (length of) stay** — treat it as a synonym for "minimum stay," not a separate concept. Generally unambiguous — maps to `minimum_stay_rules_v3` / `min_min_stay`.
- The one nuance: a client saying "MLOS for gap nights," "gap MLOS," or "orphan night rule" almost always means the `gap`/`adjacency` rule types specifically (which only exist inside `minimum_stay_rules_v3` — see Context-Preferences), **not** the separate pricing-only `gap_night` setting (Gaps & Adjacencies pricing adjustment). When a client says "gap"/"orphan" plus "MLOS" (or nothing pricing-specific at all), default to reading it as the minimum-stay rule type — clients are usually explicit ("gap price," "orphan rate") when they actually mean the pricing side instead. Only resolve toward the pricing field when the client's wording is explicitly about price/rate; don't split the difference by asking every time this specific pairing comes up.

### "Minimum price" / "price floor" / "don't go below" / "min" — and "Maximum price" / "price ceiling"
- **Aliases to expect:** "floor," "price floor," plain "min," and — especially from a property-manager audience — "owner min" or "HOA min" (an owner- or HOA-imposed floor, not a Wheelhouse concept of its own). **Wheelhouse doesn't have a distinct object or field for "owner minimum" or "HOA minimum"** — these are just minimum price rules from the client's perspective on *why* the floor exists, not a different mechanism. A client may still have organized their actual rules to reflect that distinction — e.g., using `min_min_price` (the account-wide absolute floor) specifically to encode an owner- or HOA-mandated hard floor, while using per-date `minimum_price_rules_v3` rules for the pricing team's own tactical floors. Don't assume this pattern, but do ask how the client has it organized today before writing, rather than guessing which mechanism holds their "owner min."
- Could mean the per-date `minimum_price_rules_v3` rule array, or the account-wide absolute floor `min_min_price` (symmetrically, `maximum_price_rules_v3` for per-date ceilings — there is no single account-wide absolute ceiling field the way there is a floor). "Never let this listing go below $X ever, no matter what" → `min_min_price`. "Don't go below $X during [some window]" → a `minimum_price_rules_v3` rule for that window. Also note: `min_min_price` still binds `adjustment`-type Custom Rates but not `fixed`-type ones — flag this if the client is setting a fixed Custom Rate below their stated floor.
- A client who expects one single global floor/ceiling number with no date-scoped layering may be carrying that model over from another tool — see **Context-PriceLabsMigration** for that comparison rather than guessing here.

### "Base price" / "base rate"
- Maps cleanly to `base_price`/`base_price_adjustment`, but watch for a client who says "base rate" meaning "the rate before your seasonal/event adjustments" in the general RM sense (i.e., "what does this listing rent for normally") rather than the specific API field. If they're asking a question ("what's my base rate right now") rather than requesting a change, this is fine either way; only disambiguate before a write.

### "Dynamic pricing" / "automated pricing" / "turn on pricing"
- A general industry term (used by AirDNA and others as "a revenue strategy that typically automates rate adjustments based on market conditions... instead of using fixed prices") that doesn't name any single Wheelhouse object. A client asking to "turn on dynamic pricing" could mean: (a) `automatic_rate_posting_enabled` — whether Wheelhouse actually posts its recommended prices to the channel, vs. just calculating them for review (toggle via `wheelhouse_rmPutPreferenceSetting` or `wheelhouse_rmPutPreferences`); or (b) a general question about whether the recommendation engine is active at all, which for an onboarded listing is normally always true — there's no separate "engine on/off" switch distinct from automatic rate posting and the listing's own preference configuration. Resolve by asking specifically whether they want Wheelhouse to *post* prices automatically (the concrete, writable thing) rather than trying to match "dynamic pricing" to a field by name.

### "Discount" (weekly/monthly/length-of-stay) — and "LOS pricing" / "length of stay pricing"
- **⚠️ This endpoint area is under active development — verify current field behavior against the live RM API docs before relying on the description below; don't treat it as settled.** `weekly_discount`/`monthly_discount` are flat top-level percentage fields, but they're kept in sync with `long_term_discounts.rules["7"]`/`["28"]` respectively, and the tool description notes that when both are sent in the same write, `long_term_discounts` wins. If a client already has custom `long_term_discounts` rules and asks to "change my weekly discount," clarify whether they mean the flat field or the rule-based system — writing the flat field alone may appear to do nothing if a `long_term_discounts` rule for that LOS threshold overrides it.
- **"LOS pricing" / "length of stay pricing" usually means something specific to the client, not a generic phrase** — it's their own name for a particular ruleset (often a full LOS-based discount ladder rather than just the weekly/monthly thresholds). Don't assume it maps to `long_term_discounts` by default. Given both the endpoint's active development and how often clients mean a specific configuration by this phrase, **always ask the client to spell out exactly what they mean by it, and separately confirm what's actually possible today given the current tool/endpoint and the client's own integration** (some channels support arbitrary LOS tiers via `long_term_discount_type`, others only the fixed weekly/monthly thresholds — check `supported_settings` before promising a specific shape is achievable). Treat this as a two-part clarification, not a single guess: what the client wants, and what the current endpoint can actually deliver for that listing's channel.

### "Channel"
- In ordinary RM conversation, and in almost anything a Wheelhouse client says, "channel" means the **OTA/booking channel** — Airbnb, Vrbo, Booking.com. In the API/MCP tool parameters, `channel` means the **PMS/integration connection** the listing is identified through — an entirely different concept. Every skill in this plugin uses `channel` only in the API-parameter sense (paired with `listing_id` to identify a listing). If a client says "filter by channel," "only change my Airbnb listings," or "compare channel performance," that is the OTA sense and does **not** map onto the `channel` parameter at all — it maps to a listing's `channel_ids` object or a segment filter's `source` key. Never use the bare word "channel" in a confirmation message without being explicit about which sense you mean.

### "Event" / "holiday" / "special date"
- Could mean the Wheelhouse `event`-type Season/Event entry specifically, or just "a date I care about" that might actually belong as a `custom` one-off rule or even a Custom Rate, depending on whether it recurs and whether the client wants engine-level or override-level pricing. See Context-Events&Seasons' placement decision logic — don't default to creating an Events & Seasons entry just because the client used the word "event."
- **A second, unrelated Wheelhouse sense of "event": local events as a signal inside the demand sensitivity model.** Wheelhouse's pricing engine also reacts to local/market events as part of what drives its price recommendations — but a client is far more likely to describe *that* as "dynamic pricing," "market demand," or "is the engine picking up on demand" than to call it "events." When a client says "event," default to the calendar-entry sense (Events & Seasons, above) — that's the colloquial meaning and the one this plugin's skills actually write to. But be aware the two are genuinely different features: the calendar Events & Seasons entries are something the client must explicitly create and reference from rules (nothing happens automatically just because a date is a real-world holiday), while the demand-sensitivity model's use of local events is an engine input the client doesn't configure by naming individual dates. A client may not realize both exist, or may assume that creating one automatically feeds the other — it doesn't. If a client's request sounds like it's really asking whether the engine is "aware of" upcoming demand rather than asking to set up a rule for specific dates, clarify which they mean before doing anything in Events & Seasons.

### "Replace" / "override" / "update" my rate or rule
- **Two entirely different write targets can both be called an "override," and the words alone don't tell you which:** (a) a Wheelhouse **Custom Rate** (Context-CustomRates) — a date-range price override outside the rule hierarchy; or (b) a preference rule of `custom` type, which the Wheelhouse **app's own front end labels "Date Specific"** rules (Context-Preferences) — these sit inside the ordinary rule hierarchy (at the highest precedence level, per the type-precedence table) and are not the same object as a Custom Rate at all, despite both being date-specific and both commonly called "overrides" or "date specific" by a client. The giveaway is the same one used for "custom rate" above: does the client want a one-off value that wins regardless of what the pricing engine would otherwise recommend for those dates (→ Custom Rate), or are they describing a rule that should still be read as part of the engine's own rule set, just scoped to specific dates rather than a recurring pattern (→ a `custom`-type "Date Specific" preference rule)? Don't default to Custom Rate just because the client says "override" — ask which they mean if the rest of the sentence doesn't make it clear, since a Wheelhouse-native client using the app's own UI language ("add a Date Specific rule") is very likely describing (b), not (a).
- Separately ambiguous, once the target object is settled: "change the value going forward" (an ordinary write) vs. "combine with what's already there" (compounding — additive-on-points for `adjustment`-type Custom Rates, multiplicative-on-dollars for `fixed`-type, per Context-CustomRates; ambiguous/ask-the-user for other stacked settings). Never assume "update" means compounding — the API itself never compounds automatically, so silently replacing when the client meant to stack (or vice versa) is a real, easy-to-make error. Always confirm which one per each skill's write protocol.

### "Check-in/check-out rules" vs. "availability" — and "CTA/CTD"
- Check-in/check-out day restrictions (`checkin_checkout`) are a preference setting on the pricing engine. They are unrelated to blocking/unblocking nights for booking (availability, calendar/PMS-owned) — a client asking to "close Fridays" might mean either a check-in restriction (guests can't check in on Friday, but the night can still be booked as part of a longer stay) or blocking the night outright (not bookable at all, not something any skill in this plugin writes — that's calendar/PMS territory, source of truth chain in project instructions §2). Clarify which before assuming.
- **"CTA" (Closed to Arrival) and "CTD" (Closed to Departure)** are the client's likely wording for exactly this setting — treat them as synonyms for `check_in_rules`/`check_out_rules` respectively (CTA blocks check-in on a date, CTD blocks check-out on a date), not as a different mechanism. The same availability-vs-restriction ambiguity above still applies: "CTA the 4th" could mean the pricing-engine check-in restriction or an outright calendar block, so clarify which before writing.

## Not ambiguous — use silently, no need to flag

Metrics terminology (ADR, RevPAR, Occupancy variants, etc.) — resolved silently per project instructions §3, not repeated here. Likewise `listing_id`/`channel` pairing, pagination parameters, and currency handling are mechanical API facts, not user-facing ambiguity — no need to surface these to a client at all; they're purely internal to how the skill calls the tools.

## Scope note: this file is for Wheelhouse-native users

This file's audience is a client who already thinks in Wheelhouse or general RM/STR terms and needs help mapping that language onto the right Wheelhouse write object. It deliberately does **not** carry platform-specific vocabulary from other pricing tools (PriceLabs, Key Data, AirDNA, etc.) — that's a narrower, different audience (someone migrating from or building alongside another platform) and lives in its own skill, **Context-PriceLabsMigration**, so it doesn't dilute the terminology this file's primary audience actually uses. A few entries above point there explicitly where the two audiences' confusions overlap.
