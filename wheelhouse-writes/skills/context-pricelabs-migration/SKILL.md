# Context-PriceLabsMigration

For a narrower audience than the rest of this plugin: a client whose vocabulary or expectations come from PriceLabs (or, more generally, another dynamic-pricing tool) rather than from Wheelhouse or general RM language. `${CLAUDE_PLUGIN_ROOT}/references/lexicon-disambiguation.md` deliberately stays scoped to Wheelhouse-native and general-industry terms — this skill is where PriceLabs-specific vocabulary and behavior get translated instead, so it doesn't dilute that file for the client base that never uses these terms.

**This skill is a translation layer, not a write mechanism.** It never calls a write tool itself. Its job ends at "here's the Wheelhouse object(s) that request actually targets, and here's the behavioral difference to flag" — then you hand off to the skill that actually owns that write: Context-Preferences (rules/settings), Context-CustomRates (date-range overrides), or Context-Events&Seasons (season/event definitions), or their `-api` siblings for unattended scripts.

## Always verify — don't treat this skill's mappings as fixed

Every mapping in this skill and in `references/pricelabs-customization-map.md` reflects a point-in-time read of both platforms (research performed 2026-09-15), not a permanent fact. Both sides move: the Wheelhouse RM API is beta and ships changes roughly weekly (project instructions §1/§4), and PriceLabs adds, renames, and reworks its own customizations on its own schedule that this plugin has no visibility into. Treat every row in the mapping tables — including ones marked "confirmed" — as a **starting hypothesis for this conversation**, not a settled cross-platform fact to recite back to a client as-is. Two separate things need checking, and neither substitutes for the other:

1. **Verify the Wheelhouse side live** before relying on a mapping for an actual write — check the current tool schema/RM API docs the same way Context-Preferences, Context-CustomRates, and Context-Events&Seasons already require, rather than trusting this file's field names and behavior indefinitely.
2. **Verify the PriceLabs side with the client, not from this file's research.** Don't assume a client's PriceLabs account currently has (or ever had) exactly the customization this file describes — plans, account-level feature rollouts, and PriceLabs' own product changes all mean a specific client's actual setup may differ from what's documented here. Ask the client to describe what they currently see in PriceLabs (or their own migration/integration docs) rather than asserting "PriceLabs does X" as a fact you already know to be true of their account. This applies especially to anything this file calls a "confirmed" capability or a "confirmed no analogue" gap — confirmed means confirmed against PriceLabs' public documentation as researched on 2026-09-15, not confirmed against this specific client's current plan or account.

When a mapping matters for a write that's about to happen, say what this file's research suggests, then confirm it with the client before proceeding — don't silently apply the table as ground truth. If the client's description of their PriceLabs setup conflicts with what's mapped here, trust the client and flag the discrepancy rather than insisting on this file's version.

## The three core vocabulary swaps

| PriceLabs term | What it actually is | Wheelhouse equivalent |
|---|---|---|
| **"Customization"** (any of ~29 types — see the full map below) | PriceLabs' umbrella term for essentially every pricing-engine rule type in one bucket | Usually a **Wheelhouse preference rule** (Context-Preferences) — the specific field depends on which customization; almost never a Wheelhouse Custom Rate, despite the name-association with "custom" |
| **"Pricing Profile" / "Seasonal Pricing Customization"** | A named, often-annually-recurring date range with a *bundle* of several customization settings assigned to it in one place | **No single matching Wheelhouse object.** Translate as: one Wheelhouse Season/Event entry (`custom_date_ranges`), plus each of the several preference rules the client actually wants, each separately referencing that entry's `id` (Context-Events&Seasons). Surface this as a multi-step plan before writing anything — a client asking to "set up a profile" is usually describing several Wheelhouse writes, not one. |
| **"Date-Specific Override" (DSO)** | A manual override for a specific date's price, minimum stay, or check-in/check-out rule, layered "on top of" whatever seasonal/base settings are already in effect | **Wheelhouse Custom Rate** (Context-CustomRates) for the price piece. PriceLabs' **Fixed** DSO ≈ Wheelhouse **`fixed`**-type Custom Rate (bypasses min/max); PriceLabs' **Percentage** DSO ≈ Wheelhouse **`adjustment`**-type Custom Rate (stays dynamic, respects minimum price). A DSO covering minimum-stay or check-in/check-out for a specific date has no Custom Rate equivalent at all in Wheelhouse — that's a `custom`-type preference rule instead (Context-Preferences), since Wheelhouse Custom Rates only cover price. |

## The behavioral difference that actually causes mistakes: stacking vs. precedence

This is the single most important thing to get across before writing anything for a client coming from PriceLabs, because it's not just a vocabulary gap — the two platforms produce genuinely different outcomes from the same instruction.

**PriceLabs stacks by default.** Its own documentation describes Customizations as "applied on top of our default recommendations, not replace them" — multiple customizations affecting the same date combine, with PriceLabs' own priority rules resolving conflicts among them (a hierarchy of listing > subgroup > group > account level, and within a level, fixed overrides before percentage adjustments before occupancy-based adjustments before minimum-night rules). Date-Specific Overrides layer "on top of" seasonal min/base/max specifically, not the account default. A client used to this model naturally expects "add another customization" to combine with what's already there.

**Wheelhouse does not stack — it resolves by strict precedence, and Custom Rates replace.**
- Preference rules: exactly one rule wins per date per field, decided entirely by rule `type` (the 8-level hierarchy in Context-Preferences — `global` < `day_of_week`/`monthly` < `time_based` < `seasonal` < `event` < `adjacency`/`one_sided_gap` < `gap` < `custom`, with `apply_gap_night_rules_to_overrides` flipping the last three for Minimum Stay specifically). A lower-precedence rule isn't combined with a higher one covering the same date — it's simply shadowed and has no effect for that date.
- Custom Rates: a new rate on overlapping dates shortens, splits, or replaces the existing one (Context-CustomRates) — never stacks automatically. Combining a new instruction with an existing rate is a manual computation Context-CustomRates' protocol walks through (additive-on-points for `adjustment`-type, multiplicative-on-dollars for `fixed`-type), not something either platform does for you server-side in Wheelhouse's case.

**Practical implication:** when a PriceLabs-background client asks to "add" or "layer" a change, don't assume stacking. Confirm explicitly whether they want the new instruction to combine with (requires manual math, per Context-CustomRates §"Combining values") or take precedence over (an ordinary write, possibly shadowing a lower rule instead of removing it) whatever's already there — the same "replace vs. combine" confirmation the rest of this plugin already requires, but flag here that their prior platform's default behavior (stacking) is specifically *not* what will happen if you silently proceed.

## Common customization mapping (condensed — see `references/pricelabs-customization-map.md` for the full ~29-item list)

| PriceLabs Customization | Wheelhouse equivalent |
|---|---|
| Day of Week Adjustments | `day_of_week` |
| Last Minute Prices | `last_minute_discount` (`time_based`, `days_before`) |
| Far Out Prices | `far_future_premium` (`time_based`, `days_after`) |
| Occupancy Based Adjustments | `occupancy_pacing` (Calendar Pacing) — **limitation:** PriceLabs allows grouping multiple *listings* for this adjustment (a multi-listing pool, not just units within one listing); Wheelhouse currently calculates it off a single listing only, with no multi-listing pooling equivalent (same gap as "Portfolio Occupancy Based Adjustment," below) |
| Demand Factor Sensitivity | `demand_sensitivity_rules` (Model Weights) — a separate field from Occupancy Based Adjustments above, not the same one |
| Custom Seasonal Profile | Season/Event entry (`custom_date_ranges`) + bundle of referencing rules — **or**, more simply, a `seasonal`/`event`-type rule directly on the Seasonality preference (`seasonality_adjustment`), which also ties to Season/Event entries |
| Minimum Weekend Pricing | `minimum_price_rules_v3`, `day_of_week`-type rule scoped to Sat/Sun (or `day_of_week_values`) |
| Minimum Far Out Pricing | `minimum_price_rules_v3`, `time_based`/`days_after` |
| Weekly / Monthly Discounts / Length of Stay Adjustment | `weekly_discount`/`monthly_discount`/`long_term_discounts` — see the "Discount" entry in the shared lexicon for the same-field conflict to watch for. **This whole area is under active rework on the Wheelhouse side and may change in the API docs; it's also channel-dependent on both platforms** — always verify current behavior and per-channel support before promising a specific LOS structure is portable |
| Orphan Gaps (min stay) | `minimum_stay_rules_v3`, `gap` type |
| Adjacent Day Before/After Unavailable | `minimum_stay_rules_v3`, `adjacency`/`one_sided_gap` type |
| Check-in/Check-out Restrictions | `checkin_checkout.check_in_rules`/`check_out_rules` |
| Orphan Day Prices | `gap_night` (Gaps & Adjacencies, a **pricing** setting) — don't confuse with the minimum-stay `gap`/`adjacency` rule types above; Wheelhouse keeps these as genuinely separate fields (see the shared lexicon's "Minimum stay" entry) even though PriceLabs' "orphan" naming spans both concepts |

## Capability differences worth surfacing proactively

**Wheelhouse has, without an obvious PriceLabs equivalent** — see `references/pricelabs-customization-map.md`'s dedicated "Wheelhouse features/subfeatures with no PriceLabs analogue" section for the full list and the confidence level behind each item. Highlights: a single deterministic precedence order across all rule types with an explicit, named tie-break for Minimum Stay (`apply_gap_night_rules_to_overrides`); Season/Event `id`s shared across listings until rewritten (the blank-ID protocol); Historical anchoring as a distinct Model Weight; `price_model` engine-version selection; multi-unit listing support. **Also confirmed (John, 2026-09-15) and worth leading with:** Wheelhouse's rule scoping is generally finer-grained than PriceLabs' — many settings (minimum price, minimum stay, seasonality, demand sensitivity, check-in/check-out, last-minute, far-future) let a single rule combine a time-based window with a day-of-week pattern and a specific month/date-range, a combination that doesn't appear to be available on a single PriceLabs customization; and Wheelhouse's overall write-capable API surface (notes, tags, segments, preview-before-commit, changelog, webhooks, team management) is broader than what PriceLabs' Customer API documents. Both points come from directly comparing the two platforms' API references (`references/pricelabs-customization-map.md` has the detail and the citation) — genuinely useful for a client wondering what's newly possible, but re-verify against both platforms' current docs before asserting a specific gap as settled. Surface all of this proactively — a client from PriceLabs has no reason to know to ask for it.

**PriceLabs has, without a confirmed Wheelhouse equivalent** — flag these as gaps rather than guessing a mapping:
- **Extra Person Fee** and **Pricing Offset** (a final-step markup) both have **no Wheelhouse analogue, confirmed** — both are PMS-owned in Wheelhouse's model (project instructions §2's source-of-truth chain), not something the pricing engine's preferences ever cover. Tell the client to look at their PMS integration for either, not at any Wheelhouse preference field.
- **Occupancy Based Adjustments across grouped/pooled listings**, and **Portfolio Occupancy Based Adjustment** (the bulk version) — both **confirmed no Wheelhouse analogue**, and the same underlying gap: Wheelhouse's `occupancy_pacing` computes off a single listing only, with no multi-listing grouping or portfolio-pooling equivalent today, even via the batch preference-write tools (those repeat an identical per-listing write, they don't pool occupancy across listings into one aggregated adjustment).
- **Rounding**, **Smoothing**, and **Weekend Days** redefinition — all three **confirmed (John, 2026-09-15): not currently Wheelhouse options.** No preference field applies a fixed rounding increment, smooths day-to-day price swings as its own control, or lets a client redefine which calendar days count as "weekend."
- **Neighborhood Profile Data Source** — **corrected (John, 2026-09-15): Wheelhouse's default neighborhood data is preselected, but assigning a listing to a Dynamic Set is the actual equivalent** of choosing a custom comp/market data source — not a missing capability, just a different mechanism (set membership rather than a field toggle). Dynamic Sets are a **paid feature**: `wheelhouse_rmUpgradeSet` charges the account's real payment method, so this path needs the same explicit-purchase-confirmation caution as any other purchase (project instructions §4) before suggesting it to a client.

## Write protocol (hand-off, not a write itself)

1. Identify which of the three core vocabulary swaps (or the customization map) the client's request actually maps to.
2. **Confirm the mapping with the client rather than assuming it**, per the "Always verify" section above — say what this file's research suggests, check it against the live Wheelhouse schema/docs, and ask the client to confirm what they actually see in PriceLabs before treating either side as settled.
3. If it maps to a bundle (a "profile") or spans multiple Wheelhouse objects, decompose it into the individual writes needed and say so before touching anything — same "decompose multi-step intents" discipline as Context-Preferences.
4. Explicitly flag the stacking-vs-precedence difference whenever the request implies combining with something already in place, per the section above.
5. Hand off to the owning skill (Context-Preferences / Context-CustomRates / Context-Events&Seasons, or an `-api` sibling for an unattended script) to actually confirm details and write. Don't duplicate their write protocols here.
6. If the request maps to a PriceLabs capability with no confirmed Wheelhouse equivalent, say so plainly rather than forcing a mapping — offer to verify against the live schema if it matters for the client's decision, and don't let a "confirmed no analogue" from this file's research override what the client says their PriceLabs account actually does today.
