# PriceLabs Customization → Wheelhouse Field Map

Full mapping referenced by `Context-PriceLabsMigration`. Grouped as PriceLabs itself groups them (Stay Restrictions, Pricing, Seasonal & Minimum Prices, Advanced, Bulk). "⚠️ needs verification" marks a mapping that wasn't confirmed against the live Wheelhouse schema during this plugin's build — treat as a starting hypothesis, not a confirmed fact, before telling a client it's definitely right (or definitely absent).

**This whole file is a point-in-time snapshot (researched 2026-09-15), not a permanent reference — see Context-PriceLabsMigration's "Always verify" section before using it.** Both platforms change: Wheelhouse's RM API ships roughly weekly, and PriceLabs reworks its own customizations independently of anything tracked here. Even rows marked "Confirmed" reflect PriceLabs' public documentation as it read on that date and Wheelhouse's schema as checked then — not a guarantee of a specific client's current account, plan, or configuration. Verify the Wheelhouse side against the live schema/docs, and verify the PriceLabs side with the client directly, before treating any row here as ground truth for an actual write.

**Sources for the PriceLabs side of this file:** the consumer-facing help-center articles cited in earlier research, plus PriceLabs' own developer/API reference at `https://developers.pricelabs.co/customer-api/api-reference/overview` (and its `customizations`/`date-specific-overrides-dso` endpoint pages) — check this API reference directly for anything client-facing that depends on what PriceLabs' API can actually do, since the help-center articles describe the product UI and may not reflect API-level capability or limits.

## Stay Restrictions

| PriceLabs Customization | What it does (PriceLabs) | Wheelhouse equivalent |
|---|---|---|
| Default Min Stay Rule | Base minimum nights for dates without a more specific rule | `minimum_stay_rules_v3`, a `global`-type rule (or `min_min_stay` if the client means an absolute floor rather than the default operative value) |
| Orphan Gaps | Loosens minimum stay to avoid leaving unbookable single-night gaps | `minimum_stay_rules_v3`, `gap` type |
| Last Minute Bookings (min stay) | Different minimum stay for near-term reservations | `minimum_stay_rules_v3`, `time_based` with `days_before` |
| Far-out Booking (min stay) | Different minimum stay for advance bookings | `minimum_stay_rules_v3`, `time_based` with `days_after` |
| Adjacent Day Before Unavailable | Different minimum stay when the night before is already blocked | `minimum_stay_rules_v3`, `adjacency`/`one_sided_gap` type |
| Adjacent Day After Unavailable | Different minimum stay when the night after is already blocked | `minimum_stay_rules_v3`, `adjacency`/`one_sided_gap` type |
| Lowest Minimum Stay Allowed | Absolute floor for minimum stay, regardless of other rules | `min_min_stay` |
| Check-in/Check-out Restrictions | Controls which days guests may arrive/depart | `checkin_checkout.check_in_rules`/`check_out_rules` |

## Pricing (General)

| PriceLabs Customization | What it does (PriceLabs) | Wheelhouse equivalent |
|---|---|---|
| Last Minute Prices | Custom last-minute discount/premium | `last_minute_discount` (`time_based`, `days_before`) |
| Orphan Day Prices | Custom discount/premium for orphan (single-night-gap) days | `gap_night` (Gaps & Adjacencies pricing setting) — a pricing-only field, distinct from the minimum-stay `gap`/`adjacency` rule types above despite the shared "orphan/gap" naming |
| Day of Week Adjustments | Percentage tweaks on top of algorithmic factors, per weekday | `day_of_week` |
| Occupancy Based Adjustments | Price adjustments based on occupancy rate/pace | `occupancy_pacing` (Calendar Pacing). **Confirmed limitation (corrected, John, 2026-09-15):** PriceLabs supports grouping **multiple listings** together for this adjustment (a multi-listing pool, not just multiple units within one listing — pacing computed across the group as one pooled signal); Wheelhouse's `occupancy_pacing` currently calculates off a single listing only — there's no multi-listing grouping/pooling equivalent yet. Flag this to a client migrating a grouped setup: it needs to be recreated per-listing, and the pooled behavior itself isn't reproducible today. **This is the same capability gap as "Portfolio Occupancy Based Adjustment" below** — treat the two rows as describing one underlying limitation from two angles (single-adjustment grouping vs. the dedicated bulk feature), not two separate gaps. |
| Weekly Discounts | Reduced pricing for 7+ night stays | `weekly_discount`, kept in sync with `long_term_discounts.rules["7"]` |
| Monthly Discounts | Reduced pricing for 30+ night stays | `monthly_discount`, kept in sync with `long_term_discounts.rules["28"]` |
| Length of Stay Adjustment | Rate modifications by arbitrary stay-duration tiers | `long_term_discounts` with arbitrary tiers, if the listing's channel supports `long_term_discount_type` beyond fixed weekly/monthly tiers — check `supported_settings` first. **Confirmed (John, 2026-09-15): this Wheelhouse system is actively being reworked and may change in the API docs**, and — same as the Discount/LOS-pricing entry in the shared lexicon — is only supported by some integrations/channels on the Wheelhouse side, which is expected to be true of PriceLabs' equivalent as well (verify per-channel support on both sides before promising a client a specific LOS ladder is portable). |
| Extra Person Fee | Fixed or percentage charge per additional guest | No Wheelhouse preferences equivalent. Fees are PMS-owned per the project's source-of-truth chain (Rates/MLOS → RMS; Availability/fees/taxes → PMS) — this is a different system, not a missing Wheelhouse field |

## Seasonal & Minimum Prices

| PriceLabs Customization | What it does (PriceLabs) | Wheelhouse equivalent |
|---|---|---|
| Custom Seasonal Profile | Defines a named season with its own min/base/max prices | A Wheelhouse Season/Event entry (`custom_date_ranges`) plus each referencing preference rule the client wants for that period — no single bundling object; see Context-Events&Seasons. **Confirmed (John, 2026-09-15): Seasons & Events entries are also directly available from within the Seasonality preference (`seasonality_adjustment`) itself** — a client can build the equivalent of a "custom profile" by tying a `seasonal`/`event`-type Seasonality rule to a Season/Event entry, not only by combining several separate rule types across different settings. When a client describes a "profile" that's really just adjusting the magnitude of seasonal pricing, this single-setting path is usually the simpler translation than the full multi-rule bundle. |
| Seasonality | Adjusts the magnitude of seasonal price swings | `seasonality_adjustment` — note this field only supports `seasonal`/`event`/`monthly` rule types (project instructions §7), narrower than most other settings |
| Minimum Weekend Pricing | Floor price for weekend nights specifically | `minimum_price_rules_v3`, `day_of_week`-type rule (or `day_of_week_values` on a broader rule) scoped to the weekend days |
| Minimum Far Out Pricing | Floor price for advance/far-future bookings | `minimum_price_rules_v3`, `time_based` with `days_after` |

## Advanced

| PriceLabs Customization | What it does (PriceLabs) | Wheelhouse equivalent |
|---|---|---|
| Weekend Days | Redefines which calendar days count as "weekend" | **Confirmed (John, 2026-09-15): not currently a Wheelhouse option.** No preference field lets a client redefine which calendar days count as "weekend" for weekend-scoped rules — Wheelhouse's day-of-week scoping always operates on the standard seven calendar days. |
| Demand Factor Sensitivity | Controls price volatility in response to demand signals | `demand_sensitivity_rules` (Model Weights → Demand sensitivity). **Corrected (John, 2026-09-15): this is a distinct Wheelhouse field from Occupancy Based Adjustments above** — Occupancy Based Adjustments maps to `occupancy_pacing` (Calendar Pacing), while Demand Factor Sensitivity maps to `demand_sensitivity_rules` (Model Weights). PriceLabs splitting these into two customizations lines up with Wheelhouse also treating them as two separate settings, not one field covering both. |
| Far Out Prices | Custom discount/premium for advance bookings | `far_future_premium` (`time_based`, `days_after`) — note the overlap with "Minimum Far Out Pricing" above: confirm whether the client means the *minimum floor* for far-out dates or the *recommended price adjustment* for them, since PriceLabs treats these as separate customizations and so does Wheelhouse (`minimum_price_rules_v3` vs. `far_future_premium`) |
| Neighborhood Profile Data Source | Selects which comp/market data source feeds pricing | **Corrected (John, 2026-09-15):** Wheelhouse's default neighborhood/market data is **preselected** — a listing's baseline neighborhood comparison isn't a setting a client picks. But a client **can** customize which market/comp data feeds a listing by assigning it to a **Dynamic Set** (`wheelhouse_rmPutSetAssociatedListings`/`wheelhouse_rmCreateSet`, project instructions §4) — this is the actual Wheelhouse equivalent of choosing a custom neighborhood/comp data source, just implemented as a set-membership mechanism rather than a simple field toggle. **Dynamic Sets are a paid feature** — `wheelhouse_rmUpgradeSet` charges the account's real payment method, so never suggest this path to a client without the same explicit-purchase-confirmation caution project instructions §4 requires for that tool. |
| Pricing Offset | A fixed or percentage adjustment applied as a final step after all other pricing logic — functions like a markup | **Confirmed (John, 2026-09-15): no Wheelhouse analogue.** Wheelhouse doesn't have a pricing-engine field for this; a final-step markup is instead the PMS's responsibility where the integration supports it — the same PMS-ownership pattern as Extra Person Fee above (project instructions §2's source-of-truth chain places this kind of add-on outside the RMS entirely). Don't reach for `base_price_adjustment` or any other preference field for this — tell the client to check whether their PMS integration supports a markup instead. |
| Adjacent Factor | Price modification for days surrounding an existing booking | `gap_night` (Gaps & Adjacencies) — same field as Orphan Day Prices above; PriceLabs appears to split adjacency pricing into more named customizations than Wheelhouse exposes as separate fields |
| Rounding | Rounds prices to a fixed increment (e.g., nearest $5) | **Confirmed (John, 2026-09-15): not currently a Wheelhouse option.** No preference field applies a fixed rounding increment to the final calculated price. |
| Smoothing | Reduces day-to-day price volatility across a period | **Confirmed (John, 2026-09-15): not currently a Wheelhouse option.** No preference field flattens day-to-day price swings as its own setting — the closest adjacent levers are Demand Factor Sensitivity and Historical Anchoring, but neither is a smoothing control in PriceLabs' specific sense. |

|---|---|---|

## PriceLabs' resolution hierarchy, for reference

PriceLabs resolves overlapping customizations first by **level** (Listing > Subgroup > Group > Account — most specific wins, full stop, not combined with less-specific levels), then within the winning level by **type sequence**: Fixed Price Overrides → Percentage-Based Adjustments → Occupancy-Based Adjustments → Minimum Night Requirements. Date-Specific Overrides layer on top of whatever seasonal min/base/max is active, not the account default.

This is a different axis from Wheelhouse's model entirely — Wheelhouse has no listing/subgroup/group/account inheritance for preference rules (each listing's preferences are its own), and resolves purely by rule `type` regardless of any grouping concept. Don't try to map PriceLabs' level hierarchy onto anything in Wheelhouse; it doesn't have a counterpart.

## Wheelhouse features/subfeatures with no PriceLabs analogue

The tables above map PriceLabs → Wheelhouse. This section runs the other direction: capabilities Wheelhouse exposes that don't correspond to anything on PriceLabs' own 29-item customization list (or, for a couple of items, to anything covered in this build's PriceLabs research at all). The point isn't that PriceLabs "lacks" these in some deficient sense — it's that a client building on Wheelhouse from a PriceLabs background may not think to look for them, since nothing in their prior tool trained them to expect it. Surface these proactively when relevant, rather than waiting for the client to ask.

**Confirmed absent from PriceLabs' customization list** (cross-checked against all 29 items above):

- **Historical anchoring** (`historical_anchoring_rules`, Model Weights) — a distinct model-weight lever from Demand Factor Sensitivity, with no corresponding named customization on PriceLabs' list.
- **`apply_gap_night_rules_to_overrides`** — an explicit, named toggle that flips whether `gap`/`adjacency`-type minimum-stay rules take precedence over `custom`-type ones, or vice versa. PriceLabs' resolution model is level-based (listing/subgroup/group/account) with a fixed type-sequence within a level — it has no equivalent single toggle for reordering two specific rule types against each other.
- **`price_model`** (`current`/`opt_in`) — a listing-level selector for which version of Wheelhouse's own recommendation engine is active. Nothing on PriceLabs' customization list addresses engine-version selection.
- **Season/Event `id` sharing across listings, with the blank-ID protocol for definition changes** (Context-Events&Seasons) — letting one seasonal calendar definition serve many listings until explicitly forked. PriceLabs' Custom Seasonal Profile is scoped per its own level hierarchy rather than an id shared and independently forkable per listing.
- **Multi-unit listing support** — calendar-family endpoints return one row per unit per date (`unit_number`), letting a single listing represent several independently bookable units. Nothing in the customizations list addresses sub-listing unit structure.
- **Finer sub-rule scoping across many settings — combining a time-based window, a day-of-week pattern, and a specific month/date-range on one rule.** John's assessment (2026-09-15), corroborated by fetching PriceLabs' own API reference: Wheelhouse's rule-`type` model lets many settings — minimum price, minimum stay, seasonality, demand sensitivity, check-in/check-out, last-minute, and far-future among them — combine dimensions that PriceLabs' customizations schema doesn't appear to combine on a single rule. Wheelhouse's `time_based` rules carry `days_before`/`days_after` *and* can be scoped by month or day-of-week via the same rule-type family (project instructions §7); PriceLabs' `custom_seasonal_profile` (fetched from `developers.pricelabs.co`) scopes seasons by `start_month`/`start_day`/`end_month`/`end_day` only, and `last_minute_prices` exposes a flat days-from-date threshold (`last_min_factor_dfd`) with no visible month or day-of-week scoping field alongside it. **This is based on a direct read of PriceLabs' API reference pages for `customizations` and `date-specific-overrides-dso`, not an exhaustive endpoint-by-endpoint audit** — the reference documentation itself is thin on some scoping fields, so verify against PriceLabs' current API docs (or ask the client to check their own account) before telling them a specific combination is impossible on PriceLabs' side.
- **A broader write-capable API surface overall.** Comparing endpoint inventories directly: PriceLabs' Customer API write surface (per its API reference overview, fetched 2026-09-15) centers on `listings/update`, `mappings` (map/unmap), `groups/create`, `date-specific-overrides` (listing and group level), `customizations` (listing/group/account level), and `nudges/accept`. Wheelhouse's MCP/API write-and-read surface additionally covers notes/annotations with reminders, tags/flags, a segment query language (`filter_backend`) for portfolio grouping, a preview-before-commit endpoint for preferences, a per-listing/per-preference changelog, webhooks, and team-member management — none of which have an obvious PriceLabs Customer API counterpart in what this build reviewed. Flag this as a genuine breadth difference for a client evaluating what's newly possible after migrating, but treat it as a comparison of documented endpoints as read on 2026-09-15, not a claim that PriceLabs categorically lacks these anywhere in its product (a feature could exist in the PriceLabs UI without a corresponding API endpoint, or vice versa) — re-verify against both platforms' current docs before asserting a specific capability gap to a client.

**Wheelhouse mechanisms not confirmed absent from PriceLabs' broader platform** (these come from Wheelhouse's own documented behavior, not from a gap found in the customizations research — PriceLabs may well offer comparable functionality elsewhere in its product that this build didn't research; flag with appropriate hedging, don't assert PriceLabs lacks these):

- **`supported_settings` and the `warnings` response array** — Wheelhouse tells a caller *before* writing which settings a listing's channel will actually honor, and *after* writing which ones were silently dropped and why (project instructions §6). Whether PriceLabs surfaces equivalent per-channel transparency wasn't researched for this build.
- **API-manageable Dynamic Sets** (paid comp sets with creatable/manageable membership) and a **Webhooks endpoint family** (project instructions §4) — these are account/platform features adjacent to pricing rules rather than customizations themselves, so they fall outside the 29-item list by category, not because PriceLabs was checked and found lacking.

When in doubt about which bucket a claim falls into, say what's confirmed (the first list) plainly, and hedge the second list explicitly rather than letting a client conclude PriceLabs can't do something this build simply didn't check.
